## Po co to jest

Tak wygląda typowe zadanie w firmie: procesor zarządza, a dane płyną sprzętem. Procesor przygotowuje bufor w pamięci i mówi „wyślij”, a peryferium z własnym masterem magistrali samo czyta dane, buduje pakiet i nadaje go w innej domenie zegara. Projekt łączy podział sprzęt–oprogramowanie (moduł 27), DMA i arbitraż (23.04), Ethernet (25) i CDC (15). Testbench z pamięcią, która losowo każe czekać, pokazuje, czy master Avalon jest naprawdę zgodny ze specyfikacją — to częsty temat pytań na rozmowie.

## Intuicja

Procesor jest kierownikiem: wypełnia skrzynkę (bufor), przykleja adres (rejestry) i dzwoni dzwonkiem (START). Peryferium to kurier z własnym wózkiem: samo jedzie do magazynu (DDR3), ładuje paczkę, opisuje ją etykietami (nagłówki Ethernet, IP, UDP) i dopiero gdy całość leży na rampie (kolejka), oddaje ją na taśmę (MII), która jedzie w swoim tempie i nie może stanąć w połowie.

## Teoria

### Mapa rejestrów `udp_dma`

| Słowo | Nazwa | Dostęp | Znaczenie |
|---|---|---|---|
| 0 | STER | W / RW | bit 0 START (impuls), bit 1 PRZ — zezwolenie na przerwanie |
| 1 | STATUS | R, W1C | bit 0 ZAJETY, bit 1 KONIEC (ramka wysłana, kasowanie zapisem 1) |
| 2 | ADRES | RW | adres bajtowy bufora, wyrównany do 4 B |
| 3 | DLUGOSC | RW | bajty danych UDP, 1–1472 |
| 4 / 5 | IP_ZR / IP_CEL | RW | adresy IPv4 |
| 6 | PORTY | RW | {źródłowy, docelowy} |
| 7–10 | MAC_ZR, MAC_CEL | RW | po 48 bitów w dwóch słowach |
| 11 | PAKIETY | R | licznik wysłanych ramek |

Przerwanie poziomem: `irq = KONIEC & PRZ`. Sterownik w C ([udp_dma.c](deca/udp_ddr3/software/src/udp_dma.c)) odpytuje KONIEC, przerwanie zostaje do zadania.

### Master odczytu

Avalon-MM z **potokowym odczytem**: żądanie jest przyjęte, gdy `read && !waitrequest`, a dane wracają później z `readdatavalid`, w kolejności żądań. Master pilnuje, żeby odczytów **w locie** plus słów **w buforze** było najwyżej 8 — bufor 8 słów nigdy się nie przepełni, nawet gdy składanie ramki stoi. Słowa rozkładane są na bajty od najmłodszego (little-endian, jak w Nios V).

### Ramka i przejście domeny

1. `udp_nad` (moduł 25) składa nagłówki Ethernet + IPv4 + UDP i dane; suma kontrolna IP liczona z nagłówka, suma UDP = 0 (dozwolone w IPv4).
2. Cała ramka trafia do **asynchronicznej kolejki 2048 × 9 bitów** (bit 8 — koniec ramki).
3. Dopiero gdy ramka jest w kolejce, przełącznik `ramka_t` przechodzi do domeny `tx_clk` (25 MHz z PHY), a `mii_tx` nadaje preambułę, dane i FCS. Potwierdzenie `wyslano_t` wraca i ustawia KONIEC.

Dlaczego cała ramka przed nadawaniem: MII nie ma przerwy w środku ramki. Gdyby nadajnik zaczął od razu, a DDR3 wstrzymała odczyt (odświeżanie, inny master), ramka by się urwała — klasyczny *underrun*. Bufor ramki zamienia problem czasu rzeczywistego na problem pojemności.

### Plan weryfikacji

`tb_udp_dma`: model pamięci Avalon-MM z **losowym `waitrequest` i losowym opóźnieniem** odpowiedzi, procesor modelowany zapisami rejestrów, `mii_rx` (moduł 25) odbiera ramki i sprawdza FCS, a testbench porównuje każdy nagłówek i bajt danych z pamięcią. Trzy pakiety: 1001 B (długość niepodzielna przez 4), 18 B (ramka dopełniana do 60 B), 1472 B (największy datagram) z podwójnym START w czasie pracy.

## Kod: VHDL

[hdl/vhdl/udp_dma.vhd](hdl/vhdl/udp_dma.vhd) zawiera ten sam układ; tu fragment procesu przejścia przez granicę domen — strona nadajnika (domena `tx_clk`):

```vhdl
process (tx_clk)
begin
  if rising_edge(tx_clk) then
    s_ramka <= s_ramka(0) & ramka_t;                 -- synchronizator przełącznika (2 FF)
    if tx_rst = '1' then
      nadaje <= '0'; wyslano_t <= '0';
    elsif nadaje = '0' then
      if s_ramka(1) /= wyslano_t then nadaje <= '1'; end if;   -- nowa ramka czeka w kolejce
    elsif k_czyt = '1' and k_dane(8) = '1' then      -- ostatni bajt ramki wyszedł z kolejki
      nadaje <= '0';
      wyslano_t <= s_ramka(1);                       -- potwierdzenie wraca przez synchronizator
    end if;
  end if;
end process;
```

## Kod: SystemVerilog

[hdl/sv/tb_udp_dma.sv](hdl/sv/tb_udp_dma.sv) — model pamięci 8 KB: `waitrequest` w ok. 25 % taktów i odpowiedzi z opóźnieniem 1–6 taktów (kolejność zachowana, jak wymaga Avalon):

```systemverilog
m_waitrequest <= los[3] & los[7];                  // ok. 25 % taktów wstrzymanych
if (m_read && !m_waitrequest) begin
    t_nowy = takt + 1 + (los[10:8] % 6);           // chwila odpowiedzi
    if (t_nowy < t_ost) t_nowy = t_ost;            // nie wcześniej niż poprzednia: kolejność
    t_ost = t_nowy;
    q_adr[q_og % 32] = m_address;
    q_t[q_og % 32] = t_nowy;
    q_og = q_og + 1;
end
m_readdatavalid <= 1'b0;
if (q_gl != q_og && q_t[q_gl % 32] <= takt) begin  // najstarsze żądanie gotowe: dane little-endian
    m_readdata <= {mem[q_adr[q_gl % 32] + 3], mem[q_adr[q_gl % 32] + 2], mem[q_adr[q_gl % 32] + 1],
                   mem[q_adr[q_gl % 32]]};
    m_readdatavalid <= 1'b1;
```

## Kod: Python / inne

[deca/udp_ddr3/software/src/udp_dma.c](deca/udp_ddr3/software/src/udp_dma.c) — sterownik:

```c
int udp_dma_wyslij(udp_dma_t *u, const void *bufor, uint32_t dlugosc)
{
    uintptr_t a = (uintptr_t)bufor;
    if (dlugosc == 0 || dlugosc > UDP_DMA_MAKS_DANYCH || (a & 3u) != 0 || udp_dma_zajety(u))
        return -1;
    u->baza[UDP_DMA_ADRES] = (uint32_t)a;
    u->baza[UDP_DMA_DLUGOSC] = dlugosc;
    u->baza[UDP_DMA_STER] = UDP_DMA_STER_START;   /* przerwanie wyłączone: sterownik odpytuje */
    return 0;
}
```

`main.c` wysyła 1000 datagramów po 1024 B na 192.168.1.100:5006. `system.tcl` buduje system skryptem `qsys-script`, `udp_dma_hw.tcl` opisuje komponent (interfejsy `s0`, `m0`, `irq`, eksport `mii`, osobny zegar `tx_clk`).

## Co powstaje po syntezie

Yosys: `udp_dma` — **19 442 LUT4, 19 492 FF**, prawie w całości kolejka 2048 × 9 = 18 432 bitów zamieniona na przerzutniki. W Quartusie kolejka to **2 bloki M9K**, a reszta (rejestry, master, `udp_nad` — 580 LUT4, 267 FF, `mii_tx`) mieści się w ok. 1500 elementach logicznych. Sam RAM 64 KB to 64 bloki M9K, a procesor Nios V/m — rząd 2–3 tys. LE (zależnie od opcji); w 10M50 (182 M9K) zostaje miejsce na bufor obrazu lub próbek.

## Weryfikacja

`tb_udp_dma` (Icarus, Verilator, GHDL, wyniki jednakowe):

- ramka 1: **1043 B** (dane 1001 B spod 0x100), FCS poprawny, nagłówki i dane zgodne,
- ramka 2: **60 B** (dane 18 B spod 0x1000 — dopełnienie do minimum Ethernetu), zgodna,
- ramka 3: **1514 B** (dane 1472 B spod 0x400, drugi START w czasie pracy zignorowany), zgodna,
- PAKIETY = 3, ramek odebranych 3, z błędem FCS 0, odczytów pamięci **624** (= 251 + 5 + 368 słów).

## Reguły i liczby do zapamiętania

| Reguła lub liczba | Kiedy obowiązuje |
|-------------------|------------------|
| Avalon-MM: żądanie przyjęte przy `read && !waitrequest`; dane z `readdatavalid`, w kolejności | mastery Avalon |
| Limit „w locie + w buforze ≤ pojemność bufora” — bufor nigdy się nie przepełni | każdy master z potokiem odczytu |
| Całą ramkę buforuj przed nadawaniem, jeśli źródło może się wstrzymać — MII nie ma pauzy | Ethernet, wideo, audio |
| Ethernet: ramka 64–1518 B z FCS, dane UDP ≤ 1472 B (MTU 1500 − 20 IP − 8 UDP) | UDP/IPv4 |
| 100 Mb/s: na ramkę + 8 B preambuły + 12 B przerwy; 1472 B danych → maks. ok. 95,7 Mb/s danych | przepustowość |
| Rejestr statusu W1C — skasowanie flagi bez wyścigu odczyt–modyfikacja–zapis | peryferia z flagami |
| Procesor z pamięcią podręczną danych: zapis bufora → flush przed START | Nios V/g, ARM, DMA |

## Typowe pułapki

- **Master, który zakłada stałe opóźnienie odczytu** — działa z RAM-em na chipie, psuje się z DDR3; testbench z losowym opóźnieniem to wyłapuje.
- **Za dużo odczytów w locie** — dane wracają, a bufor jest pełny; Avalon nie ma sygnału „wstrzymaj dane”.
- **Nadawanie ramki w trakcie jej czytania z DDR3** — underrun przy pierwszym odświeżaniu pamięci.
- **Brak sprawdzenia ZAJETY w sterowniku** — drugi START zmienia rejestry w trakcie pracy; tu sprzęt ignoruje START, a sterownik zwraca błąd.
- **Pamięć podręczna danych** — DMA czyta starą zawartość bufora; potrzebny flush albo bufor w obszarze niebuforowanym (bit 31 adresu w Nios).
- **Bez ARP i z adresem unicast** — komputer nie zna MAC-a FPGA, a przełącznik zgubi ramki; użyj rozgłoszeniowego MAC albo dopisz statyczny wpis ARP.

## Pytania rekrutacyjne

1. **Jak zaprojektujesz master Avalon-MM czytający blok danych z DDR3 tak, żeby nigdy nie zgubić danych?**

<details>
<summary>Odpowiedź</summary>

Żądanie liczę jako przyjęte tylko przy `read && !waitrequest`; adres i liczba słów zmieniają się dopiero wtedy. Dane przychodzą z `readdatavalid` w kolejności żądań, ale z dowolnym opóźnieniem, a odbiorca nie może ich wstrzymać, więc muszę mieć na nie miejsce: liczę odczyty w locie i słowa w buforze i zlecam nowy odczyt tylko wtedy, gdy ich suma jest mniejsza od pojemności bufora. Dla wydajności używam burstów (`burstcount`) i dłuższego bufora; testbench z losowym `waitrequest` i opóźnieniem sprawdza, że wynik jest bitowo zgodny z pamięcią.
</details>

2. **Dlaczego peryferium buforuje całą ramkę przed wysłaniem przez MII?**

<details>
<summary>Odpowiedź</summary>

MII ma stały rytm 25 MHz × 4 bity i nie pozwala na przerwę w środku ramki: `tx_en` musi trwać bez przerwy od preambuły do FCS. Źródło danych (DDR3 z odświeżaniem, magistrala współdzielona z procesorem) może się wstrzymać na nieprzewidywalny czas. Buforując całą ramkę (do 1518 B) w kolejce asynchronicznej, oddzielam niedeterministyczny odczyt od deterministycznego nadawania i przy okazji przechodzę między domenami zegara. Alternatywa: bufor tylko częściowy z gwarancją przepustowości i najgorszego opóźnienia pamięci — tańszy, ale trudniejszy do udowodnienia.
</details>

3. **Jak podzielisz pracę między procesor a sprzęt w strumieniu UDP o przepustowości bliskiej 100 Mb/s?**

<details>
<summary>Odpowiedź</summary>

Wszystko, co dotyczy każdego bajtu (odczyt bufora, sumy kontrolne, FCS, nadawanie), robi sprzęt; procesor zajmuje się tym, co rzadkie: konfiguracją adresów i portów, przygotowaniem bufora, decyzją, kiedy wysłać, obsługą błędów i ARP. Procesor 50–100 MHz nie nadąży kopiować 12 MB/s bajt po bajcie, a jedno zlecenie na ramkę to kilkanaście instrukcji. Kolejne usprawnienie to podwójne bufory (procesor wypełnia jeden, sprzęt wysyła drugi) albo kolejka deskryptorów, żeby sprzęt nie czekał na procesor między ramkami.
</details>

## Zadania

1. Dodaj kolejkę 4 deskryptorów (adres, długość) zamiast pojedynczego START, żeby procesor mógł zlecić kilka ramek naraz. **Kryterium zaliczenia:** testbench zleca 4 ramki bez czekania i sprawdza, że przerwy między nimi na MII to minimum 12 bajtów (96 bitów); trzy języki.

2. Zamień pojedyncze odczyty na bursty po 8 słów (`burstcount`). **Kryterium zaliczenia:** testbench z modelem pamięci obsługującym bursty; liczba transakcji na magistrali dla 1472 B spada z 368 do 46.

3. Uruchom wariant z DDR3 i zmierz przepustowość na komputerze. **Kryterium zaliczenia:** zrzut z Wiresharka lub skryptu z liczbą pakietów na sekundę i Mb/s, porównanie z wartością teoretyczną dla 1024 B (ok. 94 Mb/s) i wyjaśnienie różnicy.
