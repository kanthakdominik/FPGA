## Po co to jest

Ostatni projekt zamyka całą bazę: własny procesor z modułu 27 dostaje pamięć, peryferia i program, który robi coś widocznego — wita się przez UART, mruga diodami w równych odstępach z licznika sprzętowego, steruje PWM i odpowiada echem. To mikrokontroler w miniaturze, a do tego **każda warstwa jest Twoja**: RTL rdzenia, magistrala, peryferia, asembler, program i testbench, który sprawdza je razem. Taki projekt odpowiada na pytanie „czy rozumiesz, jak sprzęt i oprogramowanie się spotykają” lepiej niż jakikolwiek certyfikat.

## Intuicja

Procesor to automat, który czyta z pamięci kolejne polecenia. Peryferia udają komórki pamięci pod specjalnymi adresami: zapis pod adres GPIO zapala diody, odczyt spod adresu UART zdejmuje odebrany znak. Licznik sprzętowy tyka sam, a program tylko sprawdza flagę „minął czas” — dzięki temu odstępy nie zależą od tego, ile instrukcji program wykonał po drodze.

## Teoria

### Mapa pamięci

| Adres | Rejestr | Dostęp | Znaczenie |
|---|---|---|---|
| `0x0000_0000` | RAM 4 KB | RX/W | program i dane (1024 słowa, zapis z maską bajtów) |
| `0x1000_0000` | GPIO | W / R | LED / wejścia |
| `+0x04` | LICZNIK | R | takty od resetu |
| `+0x08` | PORÓWNANIE | RW | flaga, gdy LICZNIK = PORÓWNANIE |
| `+0x0C` | FLAGA | R, W1C | bit 0 |
| `+0x10` | UART DANE | W / R | bajt do nadania / odebrany (odczyt zdejmuje) |
| `+0x14` | UART STATUS | R, W1C | bit 0 nadajnik wolny, bit 1 jest bajt, bit 2 przepełnienie |
| `+0x18` | TOHOST | W | koniec programu (symulacja) |
| `+0x100` | `pwm_avl` | RW | STER, OKRES, WYPELN, STATUS (z 27.03) |

Dekodowanie adresu to porównanie najstarszych 4 bitów. Odczyt rejestrów, jak RAM-u, następuje w takcie po żądaniu, a wybór źródła danych odczytu — w stopniu zapisu wyniku rdzenia.

### Szczegóły, które decydują o poprawności

- **„Nadajnik wolny”** = `gotowy && !tx_start && !tx_start_d` — bez tego program sprawdzający status zaraz po zapisie zobaczyłby jeszcze stare `gotowy = 1` i nadpisał bajt (to samo zjawisko co w 31.01, tylko widziane z oprogramowania).
- **Porównanie liczone od poprzedniego porównania** (`PORÓWNANIE += OKRES`), nie od bieżącego licznika — opóźnienie obsługi flagi nie kumuluje się, odstępy są równe.
- **Pierwsze porównanie po powitaniu** — w symulacji powitanie (20 znaków × 200 taktów) trwa dłużej niż okres LED; gdyby porównanie ustawić przed nim, pierwsza flaga przyszłaby z opóźnieniem, a następne „nadrabiałyby” krótszym odstępem. Testbench wykrył dokładnie to (odstęp 1987 taktów zamiast 3000) — poprawka w programie, nie w sprzęcie.
- **Porównanie równościowe** — jeśli program spóźni się z ustawieniem porównania o więcej niż okres, flaga przyjdzie dopiero po przepełnieniu licznika (ok. 86 s przy 50 MHz). Bezpieczniejszy wariant to porównanie `LICZNIK − PORÓWNANIE ≥ 0` ze znakiem (jak `mtimecmp` w RISC-V).

### Program i narzędzia

[program/mcu.S](program/mcu.S) (75 słów): konfiguracja PWM, powitanie, potem pętla — obsługa flagi licznika (LED + 1), echo UART z zamianą małych liter na wielkie i dopisaniem LF po CR, `q` → „KONIEC”, czekanie na koniec nadawania i zapis TOHOST. Stałe czasowe są w dwóch wariantach: [program/zloz.py](program/zloz.py) dopisuje `.equ` i składa program asemblerem `rvasm.py` z modułu 27:

| Wariant | OKRES_LED | PWM | Plik |
|---|---|---|---|
| symulacja (1 MHz) | 3000 taktów | 10 / 40 | `hdl/dane/mcu_sym.hex` |
| DECA (50 MHz) | 12 500 000 (0,25 s) | 5000 / 50 000 (10 % przy 1 kHz) | `deca/rv_mcu/mcu_deca.hex`, `.mif` |

`zloz.py --sprawdz` w CI składa program jeszcze raz i porównuje z plikami w repozytorium — plik `.hex` nie rozjedzie się ze źródłem.

### Plan weryfikacji

`tb_rv_mcu` uruchamia rdzeń z programem `mcu_sym.hex` (zegar 1 MHz w skali symulacji, UART 50 kb/s = 20 taktów na bit) i sprawdza jak użytkownik: linię powitania, wypełnienie PWM w oknie 400 taktów, odstępy zmian LED (3000 ± 40), echo `Abc xyz!` → `ABC XYZ!`, pustą linię po CR LF, `q` → `KONIEC` i impuls `koniec`.

## Kod: VHDL

[hdl/vhdl/rv_mcu.vhd](hdl/vhdl/rv_mcu.vhd) — pamięć z zapisem z maską bajtów (wzorzec rozpoznawany przez Quartusa jako M9K z *byte enable*):

```vhdl
process (clk)
begin
  if rising_edge(clk) then
    if ram_sel = '1' then
      for b in 0 to 3 loop
        if d_wstrb(b) = '1' then pam(da)(8 * b + 7 downto 8 * b) <= d_wdane(8 * b + 7 downto 8 * b); end if;
      end loop;
    end if;
    d_ram <= pam(da);
  end if;
end process;
```

## Kod: Verilog

[hdl/verilog/rv_mcu.v](hdl/verilog/rv_mcu.v) — licznik, porównanie i flaga W1C:

```verilog
licznik <= licznik + 32'd1;
if (licznik == porown) flaga <= 1'b1;
if (sys_sel && zapis)
    case (d_adr[7:2])
        6'd0: led <= d_wdane;
        6'd2: porown <= d_wdane;
        6'd3: if (d_wdane[0]) flaga <= 1'b0;          // zapis 1 kasuje
        6'd4: if (tx_wolny) begin tx_bajt <= d_wdane[7:0]; tx_start <= 1'b1; end
        6'd5: if (d_wdane[2]) rx_przep <= 1'b0;
        6'd6: koniec <= 1'b1;                          // TOHOST
        default: ;
    endcase
```

## Kod: SystemVerilog

[hdl/sv/tb_rv_mcu.sv](hdl/sv/tb_rv_mcu.sv) — pomiar odstępów zmian LED:

```systemverilog
always @(posedge clk) begin
    led_p <= led;
    if (led != led_p && !rst) begin
        if (t_led >= 0) begin
            if (takt - t_led < odstep_min) odstep_min = takt - t_led;
            if (takt - t_led > odstep_max) odstep_max = takt - t_led;
        end
        t_led = takt;
        zmian = zmian + 1;
    end
end
```

## Kod: Python / inne

[program/mcu.S](program/mcu.S) — obsługa flagi licznika w pętli głównej:

```asm
petla:
    lw    t0, FLAGA(s1)          # minął okres LED?
    beqz  t0, uart
    li    t1, 1
    sw    t1, FLAGA(s1)          # skasuj flagę
    lw    t0, POROWN(s1)
    li    t1, OKRES_LED
    add   t0, t0, t1
    sw    t0, POROWN(s1)         # następne porównanie: równe odstępy niezależnie od opóźnień
    addi  s2, s2, 1
    sw    s2, GPIO(s1)
```

## Co powstaje po syntezie

Yosys (LUT4): `rv_mcu` — **65 060 LUT4, 34 694 FF**, bo RAM 1024 × 32 bity z dwoma portami odczytu zamienia się na przerzutniki i multipleksery. Sam rdzeń `rv_potok` to **3498 LUT4, 1434 FF** (w tym plik rejestrów 1772 LUT4, 1024 FF), ALU 763 LUT4. W Quartusie RAM to **4 bloki M9K**, a plik rejestrów — 2 bloki M9K albo rejestry, zależnie od stylu odczytu; cały mikrokontroler mieści się w ok. 3–4 tys. LE, czyli kilku procentach 10M50.

## Weryfikacja

`tb_rv_mcu` (Icarus, Verilator, GHDL, wyniki jednakowe):

- UART: `"RISC-V MCU (31.06)"`,
- PWM: **100** taktów stanu wysokiego na 400 (10 / 40),

## Reguły i liczby do zapamiętania

| Reguła lub liczba | Kiedy obowiązuje |
|-------------------|------------------|
| Peryferia mapowane w pamięci: dekodowanie po najstarszych bitach, odczyt z tym samym opóźnieniem co RAM | SoC |
| Flaga W1C: zapis 1 kasuje — brak wyścigu z ustawieniem sprzętowym | rejestry statusu |
| Następne porównanie = poprzednie + okres — błąd nie kumuluje się | timery, harmonogramy |
| Porównanie ze znakiem różnicy (`mtimecmp`) zamiast równości — odporne na spóźnienie | timery RISC-V |
| Status „wolny” musi uwzględniać zapis w drodze (`start` i takt po nim) | rejestry z opóźnionym skutkiem |
| Program w repozytorium jako źródło + generator; pliki `.hex` / `.mif` sprawdzane w CI | firmware w FPGA |
| RAM 1024 × 32 = 32 kbit = 4 M9K na MAX 10 | szacowanie zasobów |

## Typowe pułapki

- **Plik `.hex` nieaktualny względem `.S`** — testbench sprawdza stary program; generator z `--sprawdz` w CI usuwa ten problem.
- **Status odczytany za wcześnie po zapisie** — program widzi „wolny” i nadpisuje bajt w nadajniku.
- **Okres timera liczony od bieżącego licznika** — odstępy rosną o czas obsługi.
- **Odczyt rejestru peryferium z innym opóźnieniem niż RAM** — rdzeń dostaje dane o takt za wcześnie lub za późno; wszystkie źródła danych odczytu muszą mieć tę samą latencję.
- **Odczyt z efektem ubocznym (UART DANE zdejmuje bajt) wykonany spekulacyjnie** — rdzeń, który wykonuje `lw` na ścieżce błędnie przewidzianego skoku, gubi bajt; w `rv_potok` odczyt danych dzieje się dopiero w stopniu pamięci, po rozstrzygnięciu skoku.
- **`$readmemh` w syntezie** — Yosys tego nie obsługuje (tu `ifndef YOSYS`), Quartus potrzebuje `.mif` albo `.hex` w ścieżce projektu.

## Pytania rekrutacyjne

1. **Jak podłączysz peryferium do własnego procesora i na co uważać przy odczycie rejestrów?**

<details>
<summary>Odpowiedź</summary>

Mapuję je w przestrzeni adresowej: dekoder po najstarszych bitach adresu wybiera RAM albo peryferium, zapis idzie do rejestru przy `wstrb != 0`, a dane odczytu wybiera multiplekser. Najważniejsze, żeby odczyt peryferium miał dokładnie taką samą latencję jak RAM (tu 1 takt, wybór źródła w stopniu zapisu wyniku), inaczej rdzeń dostanie złe dane. Odczyty z efektem ubocznym (zdejmowanie bajtu z kolejki, kasowanie flagi) mogą się wykonać tylko raz i tylko dla instrukcji, które naprawdę zostaną zatwierdzone — w potoku odczyt musi być po rozstrzygnięciu skoków albo peryferium musi tolerować spekulację.
</details>

2. **Program ma zmieniać LED co 0,25 s, ale w międzyczasie obsługuje UART. Jak zapewnić równe odstępy?**

<details>
<summary>Odpowiedź</summary>

Liczenie czasu oddaję sprzętowi: licznik swobodny i rejestr porównania ustawiający flagę (albo przerwanie). Następne porównanie wyliczam jako poprzednie + okres, a nie licznik + okres, więc opóźnienie obsługi flagi wpływa tylko na chwilę reakcji, a nie na kolejne odstępy (brak dryfu). Pierwsze porównanie ustawiam tuż przed pętlą główną, po długich operacjach inicjalizacji. Jeśli obsługa może się spóźnić o cały okres, stosuję porównanie ze znakiem różnicy zamiast równości.
</details>

3. **Jak weryfikujesz jednocześnie sprzęt i program w takim mikrokontrolerze?**

<details>
<summary>Odpowiedź</summary>

Testbench systemowy uruchamia RTL z prawdziwym programem złożonym z repozytorium i sprawdza zachowanie na zewnętrznych wyprowadzeniach: dekoduje UART, mierzy PWM i odstępy LED, wysyła znaki i porównuje echo, a koniec programu sygnalizuje zapis TOHOST. Stałe czasowe w wariancie symulacyjnym są skrócone, logika ta sama. Do tego testy jednostkowe rdzenia (moduł 27: zestaw instrukcji, hazardy) i peryferiów osobno oraz sprawdzenie w CI, że plik programu odpowiada źródłu. Błąd znaleziony tu (odstęp 1987 zamiast 3000) był błędem programu, nie sprzętu — test systemowy wykrywa oba rodzaje.
</details>
