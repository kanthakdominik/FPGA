## Po co to jest

Mapa rejestrów z [21.02](21.02-rejestry-sterujace-axi4-lite-i-avalon-mm.md) żyje w kilku miejscach naraz: w RTL, w sterowniku C (`#define STER 0x04`), w dokumentacji dla programistów, w modelu rejestrów testbencha (UVM RAL) i w skryptach testowych. Ręczna synchronizacja tych kopii to klasyczne źródło błędów — bit przesunięty w dokumentacji, rejestr dodany w RTL, ale nie w sterowniku. W przemyśle mapę opisuje się **raz**, w języku opisu rejestrów, a wszystkie postacie generuje narzędzie. SystemRDL (Accellera) to otwarty standard takiego opisu, a PeakRDL — darmowy zestaw generatorów: blok rejestrów w SystemVerilogu z gotowym slave'em AXI4-Lite/Avalon-MM/APB, nagłówki C, dokumentacja HTML, model UVM.

## Intuicja

Jeden plan budynku zamiast osobnych rysunków dla elektryka, hydraulika i portiera. Z planu drukuje się każdą wersję potrzebną komuś innemu; gdy przesunie się ścianę, wszystkie wersje zmieniają się naraz.

## Teoria

### Komponenty SystemRDL

- **field** — pole bitowe z właściwościami: dostęp programowy `sw` (r, w, rw), dostęp sprzętowy `hw` (r, w, rw, na), wartość po resecie, zachowanie przy zapisie `onwrite` (np. `woclr` — zapis jedynki kasuje, `woset`, `wot` — przełączenie) i przy odczycie `onread` (`rclr` — odczyt kasuje),
- **reg** — rejestr złożony z pól (`regwidth`, `accesswidth`),
- **regfile** — grupa rejestrów (np. powtarzana tablica kanałów),
- **addrmap** — przestrzeń adresowa bloku: rejestry pod adresami (`@ 0x04`) albo rozmieszczone automatycznie.

### Właściwości, które zastępują ręczną logikę

| Zachowanie z 21.02 | SystemRDL |
|---|---|
| RW, sterowanie sprzętu | `field { sw = rw; hw = r; }` |
| RO, stan ze sprzętu | `field { sw = r; hw = w; }` |
| stała (ID) | `field { sw = r; hw = na; } id[31:0] = 32'h21020001;` |
| W1C, ustawiane przez sprzęt | `field { level intr; sw = rw; onwrite = woclr; }` — `intr` daje bit lepki ustawiany przez sprzęt |
| maska przerwań | `PRZER.zd->enable = MASKA.m;` — przerwanie rejestru tylko z bitów włączonych maską |

Generator tworzy też sygnał przerwania rejestru (`hwif_out.PRZER.intr`), impulsy zapisu i odczytu (`swmod`, `swacc`) dla pól, które muszą wywołać akcję, liczniki (`counter`) i wiele innych konstrukcji — wszystkie z tą samą, sprawdzoną logiką.

### PeakRDL-regblock — wygenerowany blok rejestrów

Generator tworzy dwa pliki: pakiet ze strukturami wejść i wyjść sprzętowych (`hwif_in`, `hwif_out`) i moduł z wybranym **interfejsem CPU** (`--cpuif`: `axi4-lite`, `axi4-lite-flat`, `avalon-mm`, `apb4`, `passthrough`…). Logika użytkownika nie dotyka protokołu magistrali: czyta `hwif_out.STER.ster.value`, wystawia `hwif_in.STAN.stan.next`, a zdarzenia podaje na `hwif_in.PRZER.zd.next`. To ten sam podział co `rejestry_rdzen` plus adaptery w 21.02 — tyle że generowany i bez możliwości pomyłki w adresach.

### Dlaczego nie tylko generator

Generator rozwiązuje spójność, ale projektant nadal musi: zaprojektować mapę (grupowanie, rezerwy na rozbudowę, wyrównanie), wybrać zachowania pól (W1C zamiast RC, impuls zamiast bitu do ręcznego kasowania), zweryfikować integrację (czy sprzęt poprawnie używa wyjść bloku) i rozumieć wygenerowany kod przy debugowaniu. Dlatego kurs ma zarówno ręczny `rejestry_rdzen` (21.02), jak i opis RDL tej samej mapy — `sprawdz.py` porównuje oba źródła, a w projekcie produkcyjnym ręczny kod byłby zastąpiony wygenerowanym.

## Schemat i przebiegi

```
                          ┌─► peakrdl regblock ─► build/rejestry_pkg.sv, rejestry.sv  (slave AXI4-Lite + rejestry)
 rdl/rejestry.rdl ──┬─────┼─► peakrdl c-header ─► build/rejestry.h                    (sterownik C)
   (jedno źródło)   │     └─► peakrdl html     ─► build/html/                         (dokumentacja)
                    └─► sprawdz.py (systemrdl-compiler): tabela rejestrów + zgodność z hdl/verilog/rejestry_rdzen.v

 wygenerowany blok:
   s_axil_aw*, s_axil_w*, s_axil_b*, s_axil_ar*, s_axil_r* ◄──► rejestry ◄── hwif_in  (stan, zdarzenia)
                                                                        ──► hwif_out (ster, maska, intr)
```

## Kod: VHDL

Kurs nie generuje tu VHDL: PeakRDL-regblock produkuje SystemVerilog — w projekcie VHDL łączy się go jak każdy moduł w innym języku (Quartus i Vivado mieszają języki w jednym projekcie). VHDL-owy odpowiednik ręczny to [hdl/vhdl/rejestry_rdzen.vhd](hdl/vhdl/rejestry_rdzen.vhd) z 21.02 — z tą samą mapą, sprawdzaną z RDL przez `sprawdz.py` (adresy z wersji Verilog, a testy z trzech języków pilnują, że wersje się zgadzają).

## Kod: Verilog

[rdl/rejestry.rdl](rdl/rejestry.rdl) — opis mapy (SystemRDL ma składnię podobną do SystemVerilogu):

```systemverilog
addrmap rejestry {
    name = "Rejestry kursu FPGA (21.02)";
    default regwidth = 32;

    reg { field { sw = r;  hw = na; } id[31:0] = 32'h21020001; } ID   @ 0x00;
    reg { field { sw = rw; hw = r;  } ster[31:0] = 0;          } STER @ 0x04;
    reg { field { sw = r;  hw = w;  } stan[31:0];              } STAN @ 0x08;
    reg {
        field { level intr; sw = rw; onwrite = woclr; } zd[7:0] = 0;   // W1C, ustawiane przez sprzęt
    } PRZER @ 0x0C;
    reg { field { sw = rw; hw = r;  } m[7:0] = 0;              } MASKA   @ 0x10;
    reg { field { sw = rw; hw = na; } d[31:0] = 0;             } SKRYTKA @ 0x14;

    PRZER.zd->enable = MASKA.m;                                         // irq = |(PRZER & MASKA)
};
```

## Kod: SystemVerilog

Porty bloku wygenerowanego przez `peakrdl regblock rejestry.rdl --cpuif axi4-lite-flat` (wynik z CI, skrócony):

```systemverilog
module rejestry (
        input wire clk,
        input wire rst,
        output logic s_axil_awready,
        input wire s_axil_awvalid,
        input wire [4:0] s_axil_awaddr,
        input wire [2:0] s_axil_awprot,
        ...
        output logic [31:0] s_axil_rdata,
        output logic [1:0] s_axil_rresp,
        input rejestry_pkg::rejestry__in_t hwif_in,
        output rejestry_pkg::rejestry__out_t hwif_out
    );
```

Adres ma 5 bitów, bo mapa zajmuje 24 bajty (do 0x17). Python z biblioteką systemrdl-compiler ([rdl/sprawdz.py](rdl/sprawdz.py)) przechodzi po drzewie elaboracji:

```python
rdlc = RDLCompiler()
rdlc.compile_file(str(tu / "rejestry.rdl"))
top = rdlc.elaborate().top
for reg in top.registers():
    for f in reg.fields():
        print(reg.absolute_address, reg.inst_name, f.inst_name, f.msb, f.lsb, f.get_property("sw").name)
```

## Co powstaje po syntezie

Wygenerowany `rejestry.sv` ma ok. 16 KB kodu (pakiet 1,6 KB): dekoder adresu, rejestry pól z logiką `woclr`/`intr`, multiplekser odczytu i slave AXI4-Lite z obsługą WSTRB. Logicznie odpowiada ręcznemu `axil_rejestry` + `rejestry_rdzen` z 21.02 (191 LUT4 i 158 przerzutników w syntezie ogólnej Yosysa). W CI wygenerowany kod przechodzi lint Verilatora bez błędów; tryb `-Wall` zgłasza 13 ostrzeżeń stylu (m.in. MULTIDRIVEN dla pól jednej struktury pisanych w różnych blokach `always_comb` — to cecha generatora, nie błąd logiczny). Wygenerowanego kodu się nie poprawia ręcznie — ostrzeżenia wycisza się w konfiguracji lintu dla katalogu `build/`.

## Weryfikacja

W CI (zadanie *Weryfikacja open source*, krok *Mapa rejestrów — SystemRDL i PeakRDL*) skrypt [rdl/generuj.sh](rdl/generuj.sh):

1. `sprawdz.py` kompiluje RDL, drukuje tabelę rejestrów i sprawdza zgodność z `rejestry_rdzen.v` — adresy sześciu rejestrów i wartość ID są takie same w obu źródłach:

| Adres | Rejestr | Pole | Bity | Dostęp SW | Dostęp HW | Reset |
|---|---|---|---|---|---|---|
| 0x00 | ID | id | 31:0 | r | na | 0x21020001 |
| 0x04 | STER | ster | 31:0 | rw | r | 0x0 |
| 0x08 | STAN | stan | 31:0 | r | w | — |
| 0x0C | PRZER | zd | 7:0 | rw (woclr) | rw | 0x0 |
| 0x10 | MASKA | m | 7:0 | rw | r | 0x0 |
| 0x14 | SKRYTKA | d | 31:0 | rw | na | 0x0 |

2. `peakrdl regblock`, `peakrdl c-header`, `peakrdl html` — wszystkie trzy postacie powstają z jednego pliku; nagłówek C zawiera dla każdego pola maskę, pozycję, szerokość i wartość po resecie (`REJESTRY__STER__STER_bm 0xffffffff`, `…_bp 0`, `…_bw 32`, `…_reset 0x0`) oraz strukturę rejestrów do odwzorowania w pamięci,
3. lint wygenerowanego SystemVerilogu.

Zmiana adresu w RDL bez zmiany w RTL (albo odwrotnie) kończy krok błędem — tak w praktyce pilnuje się spójności, dopóki ręczny kod nie zostanie zastąpiony generowanym.

## Reguły i liczby do zapamiętania

| Reguła lub liczba | Kiedy obowiązuje |
|-------------------|------------------|
| Mapa rejestrów ma jedno źródło; RTL, C, dokumentacja i model UVM są generowane | każdy projekt z oprogramowaniem |
| SystemRDL: addrmap → regfile → reg → field | struktura opisu |
| `sw`/`hw` — dostęp programowy i sprzętowy; `onwrite = woclr` — W1C; `intr` — bit lepki ustawiany przez sprzęt | właściwości pól |
| PeakRDL-regblock: logika rejestrów + wybierany interfejs CPU (AXI4-Lite, Avalon-MM, APB) | generowany slave |
| Wygenerowanego kodu nie edytuje się — zmienia się opis | przepływ pracy |
| Gdy kod jest ręczny, test porównuje go z opisem | okres przejściowy |

## Typowe pułapki

- **Ręczne poprawki w wygenerowanych plikach** — znikają przy następnej generacji; zmiany wprowadza się w RDL albo w szablonach generatora.
- **Pola z `onread = rclr`** (kasowanie odczytem) — wygodne w opisie, groźne w praktyce (debugger, odczyt spekulatywny); W1C jest bezpieczniejsze.
- **Brak `accesswidth`/`regwidth` zgodnych z magistralą** — zapisy 8- i 16-bitowe z procesora traktowane inaczej, niż zakłada sterownik.
- **Generowanie w każdym budowaniu bez kontroli wersji narzędzia** — inna wersja PeakRDL może zmienić nazwy w `hwif` i zepsuć integrację; wersje narzędzi przypina się w `requirements.txt` w projekcie produkcyjnym.
- **Rejestry bez rezerwy w mapie** — dodanie rejestru przesuwa wszystkie następne adresy; zostawia się luki i stałe adresy grup.

## Pytania rekrutacyjne

1. **Po co opisywać rejestry w SystemRDL albo IP-XACT, skoro RTL można napisać ręcznie?**

<details>
<summary>Odpowiedź</summary>

Bo mapa rejestrów jest potrzebna w wielu postaciach — RTL, nagłówki i sterowniki C, dokumentacja, model rejestrów UVM, skrypty testowe — i ręczne utrzymywanie ich spójności prowadzi do błędów, które wychodzą dopiero przy integracji z oprogramowaniem. Opis w jednym języku generuje wszystkie postacie naraz, standaryzuje zachowania pól (W1C, impulsy, liczniki) i pozwala zmieniać magistralę bez zmiany logiki rejestrów.
</details>

2. **Jak opisać w SystemRDL rejestr flag przerwań z maską?**

<details>
<summary>Odpowiedź</summary>

Pole flag jako `intr` (bit lepki ustawiany przez sprzęt) z `sw = rw` i `onwrite = woclr` — zapis jedynki kasuje. Osobny rejestr maski z polem `sw = rw`. Połączenie właściwością `enable` (albo `mask`) pola przerwań: `FLAGI.pole->enable = MASKA.pole;`. Generator tworzy wyjście przerwania rejestru (OR bitów włączonych maską) i wejścia zdarzeń dla sprzętu.
</details>

3. **Czym różni się generowany blok rejestrów od ręcznie napisanego slave'a, jeśli chodzi o weryfikację?**

<details>
<summary>Odpowiedź</summary>

Generator jest zweryfikowany przez jego autorów dla wszystkich obsługiwanych konstrukcji, więc nie testuje się ponownie protokołu i logiki pól w każdym projekcie — wystarczy test integracji: czy sprzęt poprawnie używa wyjść i wejść `hwif`, czy adresy w oprogramowaniu pochodzą z wygenerowanego nagłówka. Ręczny slave wymaga pełnej weryfikacji protokołu (jak `tb_rejestry` w 21.02). Generator daje też model rejestrów (UVM RAL), z którego testbench korzysta zamiast ręcznych adresów.
</details>
