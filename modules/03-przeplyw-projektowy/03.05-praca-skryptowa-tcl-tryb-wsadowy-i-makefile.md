## Po co to jest

Projekt prowadzony wyłącznie w GUI jest nie do odtworzenia: ustawienia klikane w oknach giną, a kolega dostaje inny wynik. W zespołach projekty FPGA buduje się skryptami — tak samo na komputerze projektanta, jak w CI. Tcl jest językiem skryptowym Quartusa, Vivado, Questy i większości narzędzi EDA, więc jego podstawy przydają się wszędzie. Ta baza od początku tworzy projekty skryptami; tu wyjaśniamy, jak to działa.

## Intuicja

GUI Quartusa to tylko nakładka: każde kliknięcie wywołuje polecenie Tcl, a każdy etap kompilacji to osobny program. Skrypt robi to samo co kliknięcia, ale zawsze tak samo, można go zapisać w repozytorium i uruchomić bez ekranu (na serwerze CI). Makefile dokłada do tego pamięć o zależnościach: „skompiluj ponownie tylko wtedy, gdy zmienił się któryś plik źródłowy”.

## Teoria

### Tcl w pigułce

```tcl
set okres 20.0                        ;# zmienna
puts "Okres: $okres ns"               ;# podstawienie zmiennej
set f [expr {1000.0 / $okres}]        ;# [ ] wykonuje polecenie i wstawia wynik
foreach led {LED[0] LED[1]} {         ;# { } — tekst dosłowny, bez podstawień
    puts "Dioda: $led"
}
proc pin {nazwa numer} {              ;# procedura
    set_location_assignment $numer -to $nazwa
}
if {$f > 40} { puts "szybki zegar" } else { puts "wolny zegar" }
set piny [dict create {LED[0]} PIN_C7]  ;# słownik — nazwa z [ ] w klamrach
dict get $piny {LED[0]}
```

Najważniejsze zasady Tcl: wszystko jest tekstem; `$x` podstawia wartość zmiennej, `[polecenie]` — wynik polecenia, a `{…}` blokuje podstawienia. Dlatego nazwę sygnału `LED[0]` w miejscu, gdzie Tcl wykonałby podstawienie, trzeba ująć w nawiasy klamrowe: `{LED[0]}` — inaczej standardowy Tcl spróbuje wykonać polecenie `0`. Pliki QSF zapisywane przez Quartusa zawierają takie nazwy bez klamer i Quartus je toleruje, ale w skryptach bezpieczniej zawsze używać klamer.

### Tryb wsadowy Quartusa

| Polecenie | Co robi |
|-----------|---------|
| `quartus_sh -t skrypt.tcl arg1 arg2` | wykonuje skrypt Tcl (argumenty w `$quartus(args)`) |
| `quartus_sh --flow compile projekt` | pełna kompilacja |
| `quartus_map projekt` | analiza i synteza |
| `quartus_fit projekt` | rozmieszczanie i trasowanie |
| `quartus_asm projekt` | pliki `.sof`/`.pof` |
| `quartus_sta projekt` | analiza czasowa (domyślne raporty) |
| `quartus_sta -t skrypt.tcl projekt` | analiza czasowa ze skryptem (własne raporty, sprawdzenia) |
| `quartus_pgm -c 1 -m jtag -o "p;plik.sof"` | programowanie |
| `jtagconfig` | lista programatorów i urządzeń w łańcuchu JTAG |

Pakiety Tcl: `::quartus::project` (tworzenie projektu, przypisania), `::quartus::flow` (`execute_flow -compile`), `::quartus::sta` (analiza czasowa: `create_timing_netlist`, `report_timing`), `::quartus::report` (odczyt raportów).

### Makefile

Makefile opisuje **cele** i ich **zależności**. `make` odbudowuje cel tylko wtedy, gdy któraś zależność jest nowsza. Fragment [deca.mk](../../plytka-deca/deca.mk):

```make
ZNACZNIK := .projekt-$(JEZYK)
ZRODLA   := $(wildcard deca_top.$(ROZSZ) *.sdc ../../hdl/$(JEZYK)/*.$(ROZSZ))

$(ZNACZNIK): utworz_projekt.tcl            # projekt od nowa przy zmianie skryptu lub języka
	rm -f .projekt-*
	$(QSH) -t utworz_projekt.tcl $(JEZYK) $(UKLAD)
	touch $@

$(SOF): $(ZNACZNIK) $(ZRODLA)              # kompilacja, gdy zmienił się kod lub ograniczenia
	$(QSH) --flow compile $(PROJEKT)

sram: $(SOF)
	$(QPGM) -c $(KABEL) -m jtag -o "p;$(SOF)"
```

Plik znacznika `.projekt-<język>` zapamiętuje, w jakim języku utworzono projekt — zmiana `JEZYK=vhdl` tworzy projekt od nowa.

### Kompilacja w CI

Quartus Prime Lite jest bezpłatny i działa w trybie wsadowym na Linuksie, także w kontenerze. Typowy potok CI dla projektu FPGA:

1. lint i symulacja (szybko, przy każdej zmianie) — w tej bazie: [.github/workflows/checks.yml](../../.github/workflows/checks.yml),
2. synteza i implementacja (wolno — minuty do godzin; często nocą albo przy scalaniu zmian),
3. sprawdzenie raportów: brak ostrzeżeń krytycznych, dodatni zapas (`sprawdz_czasy.tcl`),
4. archiwizacja plików `.sof`/`.pof` z numerem wersji.

Ta baza uruchamia w CI tylko otwarte narzędzia (punkt 1 i kompilację modułów nadrzędnych DECA w GHDL, Icarusie i Verilatorze) — instalator Quartusa ma kilka GB.

## Na płytce DECA

```bash
cd modules/00-srodowisko-pracy/deca/blink
make                    # projekt (Verilog) + pełna kompilacja
make czas               # zapas setup/hold we wszystkich modelach, PASS/FAIL
make sram               # wgranie do SRAM
make JEZYK=vhdl sram    # to samo z wersją VHDL — projekt powstanie od nowa
make flash              # wgranie do pamięci flash
make czysc              # usunięcie plików generowanych
```

Na Windowsie `make` jest dostępny w MSYS2 albo WSL; bez niego wystarczą polecenia `quartus_sh` z [00.06](../00-srodowisko-pracy/00.06-pierwszy-projekt-migajaca-dioda-w-trzech.md).

## Reguły i liczby do zapamiętania

| Reguła lub liczba | Kiedy obowiązuje |
|-------------------|------------------|
| GUI to nakładka na polecenia Tcl i programy wsadowe | Quartus, Vivado |
| `quartus_sh -t skrypt.tcl` — skrypt; `--flow compile` — pełna kompilacja | Quartus |
| Tcl: `$` — zmienna, `[ ]` — polecenie, `{ }` — bez podstawień | każdy skrypt |
| Nazwy z nawiasami kwadratowymi w Tcl — w `{ }` | `LED[0]`, `KEY[*]` |
| Projekt odtwarzalny = skrypty + źródła w repozytorium, bez plików generowanych | praca zespołowa |

## Typowe pułapki

- **`LED[0]` bez klamer w Tcl.** Standardowy Tcl próbuje wykonać polecenie `0` i zgłasza błąd *invalid command name "0"*; to, że Quartus toleruje takie nazwy w QSF, nie dotyczy każdego miejsca w skryptach.
- **Ustawienia klikane w GUI, a projekt tworzony skryptem.** Następne uruchomienie skryptu nadpisze QSF — zmiany giną. Dopisz je do skryptu.
- **Ścieżki bezwzględne w skryptach.** Nie zadziałają u kolegi ani w CI. Używaj ścieżek względnych od położenia skryptu (`[info script]`).
- **Wcięcia spacjami w Makefile.** Polecenia reguł muszą zaczynać się od tabulatora.

## Pytania rekrutacyjne

1. **Dlaczego projekty FPGA buduje się skryptami, a nie z GUI?**

<details>
<summary>Odpowiedź</summary>

Dla odtwarzalności i automatyzacji: skrypt w repozytorium daje ten sam wynik u każdego członka zespołu i w CI, ustawienia są widoczne w historii zmian, a kompilację można uruchomić na serwerze bez ekranu, z automatycznym sprawdzeniem raportów. GUI służy do analizy (przeglądanie raportów, schematów, ścieżek), nie do definiowania projektu.
</details>

2. **Jak w skrypcie sprawdzisz, czy projekt spełnia wymagania czasowe?**

<details>
<summary>Odpowiedź</summary>

Uruchamiam `quartus_sta -t` ze skryptem, który otwiera projekt, tworzy sieć czasową, wczytuje SDC i dla każdego modelu pracy pobiera najgorszy zapas setup i hold (np. `report_timing -npaths 1` zwraca liczbę ścieżek i najgorszy zapas). Przy ujemnym zapasie skrypt kończy się kodem błędu, co zatrzymuje CI. W Vivado podobnie: `report_timing_summary` i odczyt WNS/WHS.
</details>

## Zadania

1. Uruchom `make`, `make czas` i `make JEZYK=sv sram` dla projektu `logika` z modułu 01. **Kryterium zaliczenia:** `make czas` kończy się `PASS`, a ponowne `make` bez zmian w plikach nic nie kompiluje.

2. Napisz skrypt Tcl dla `quartus_sh -t`, który otwiera projekt `blink` i wypisuje wszystkie przypisania pinów (`get_all_assignments -type instance -name LOCATION`). **Kryterium zaliczenia:** lista sygnałów z numerami pinów zgodna z [piny.md](../../plytka-deca/piny.md).

<details>

```tcl
package require ::quartus::project

}

```
</details>
